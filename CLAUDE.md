# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

## Project overview

buddy-on is a first-line support bot: questions come in over REST, answers are
generated by a **local LLM** (Ollama over the LAN) grounded in RAG over
indexed docs and code. Single deployable app in `apps/server` (Node 22,
TypeScript, Fastify). Postgres + pgvector stores chunks and vectors, RabbitMQ
carries jobs, LangGraph.js orchestrates the answer graph.

Read `SIZING.md` before touching retrieval or generation settings — it holds
the measured numbers (throughput, latency, what failed at scale) that most of
the non-obvious decisions below are based on.

## Commands

All run from `apps/server/`:

```bash
npm run dev              # tsx watch; HTTP + worker in one process, seed-indexes on boot
npm run build            # tsc
npm run typecheck        # tsc --noEmit — the main gate, run before finishing any task
npm run prisma:migrate   # create/apply a migration in dev
npm run prisma:deploy    # apply migrations (used by Docker/boot)
npm run index -- <dir> [collection]   # ad-hoc indexing
npm run search -- "query"             # retrieval only, no LLM — use to debug RAG
npm run ask -- "question"             # full graph from the terminal
```

Infra for local dev: `docker compose up -d postgres rabbitmq` (repo root).
There are no unit tests; `typecheck` + a manual `ask`/`search` run is the
verification loop.

## Architecture

Request flow: `api/routes/messages` → `queue/jobs` (Job row + publish) →
RabbitMQ → `queue/worker` (prefetch = WORKER_CONCURRENCY) → `graph/support`
(retrieve → generate → guard) → Job updated → client polls `/status/:jobId` or
gets a `queue/webhook` POST.

- `graph/support.ts` — the main graph; `graph/agentic.ts` — optional ReAct
  loop (Tier 2+ models only); `graph/guard.ts` — post-answer grounding check.
- `rag/` — `indexer` (walk → chunk → embed → pgvector, sha256-incremental),
  `chunker` (markdown by headings, code by lines), `search` (vector | lexical |
  hybrid via RRF), `expand` (LLM query expansion for the lexical arm).
- `queue/connection.ts` — the only RabbitMQ entry point: `registerTopology` /
  `addConsumer` / `publish` survive broker restarts (reconnect, re-declare,
  re-subscribe). Never hold a raw channel outside this module.
- `indexing/` — startup seed-index (a server must never answer against an
  empty index) + cron-triggered re-index via a RabbitMQ message (prefetch=1).
- Prisma models: `User`, `Job`, `DocChunk`, `AnswerCache`; enums `JobStatus`,
  `JobKind`, `MessageChannel`.

## Two config layers — keep them separate

- **`.env`** (`src/config/index.ts`) — infra and secrets only: DB, RabbitMQ,
  Ollama URL, JWT, ports, worker concurrency.
- **`buddy.config.yaml`** (`src/config/appConfig.ts`, zod-validated) —
  behavior: model, temperature, `think`, retrieval mode/topK/minScore, the
  `profile` preset, sources, reindex schedule, system prompt.

New knobs go into the yaml + zod schema, not into `process.env` reads inside
features. Relative source paths resolve against the config file.

## LLM conventions (the non-obvious parts)

- **All model calls go through `llm/chat.ts` / `llm/ollama.ts`** — they carry
  timeouts and retries (Ollama over the network flickers). Don't instantiate
  `ChatOllama` ad-hoc in features.
- **`think: false` is deliberate.** Gemma 4 with thinking enabled burns the
  token budget on reasoning and can return an *empty* answer under a cap; it
  broke rule extraction and agentic tool calls. Don't enable it without
  re-testing those paths.
- **The `profile` preset (`fast`/`balanced`/`quality`/`max`) maps to LLM-pass
  flags** (`expandQuery`, `groundingCheck`, `agentic`) in `appConfig.ts`. If
  you add a new LLM pass, wire it into that mapping; `custom` must keep
  honoring explicit flags.
- **`agentic: true` needs a Tier 2+ model.** On 12B the ReAct loop measurably
  loses to single-shot (vaguer answers, higher latency) — see SIZING.md.
- **Guard parsing:** `"UNSUPPORTED"` contains `"SUPPORTED"` as a substring —
  always check the negative first (`graph/guard.ts`).
- **The system prompt is end-user-facing.** It must never mention files, code,
  functions or "the context" — answers read as product knowledge. Keep that
  contract when editing prompts.

## Data & queue conventions

- pgvector operations (HNSW index, cosine search, `to_tsquery('simple', ...)`)
  are **raw SQL** in `rag/search.ts` / `rag/indexer.ts` — Prisma doesn't cover
  them. Keep raw SQL contained to those files.
- Incremental indexing dedups chunks by sha256. Changing chunker parameters
  (sizes, overlap) silently invalidates every hash → next index run re-embeds
  everything. Fine, but expect it and say so in the PR.
- Workers **ack on failure too** — the failed status is already in the DB;
  endless redelivery is worse than a recorded failure. Don't "fix" this.
- Schema changes go through `prisma migrate dev`, never by editing SQL in
  existing migrations.

## Workflow

- Verify RAG changes with `npm run search` (retrieval quality) before blaming
  the model; the measured failure modes in SIZING.md ("symptom → mechanism"
  questions, cross-file rules) are retrieval problems, not generation problems.
- No git operations (add/commit/push) unless explicitly asked.
